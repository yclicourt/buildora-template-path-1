# Backend (Django + Django REST Framework)

API for {{PROJECT_TITLE}}: project structure, PostgreSQL + Redis configuration, CORS for the Vite dev server, and a health endpoint. Auth: JWT authentication (SimpleJWT) with email login, token blacklist on logout, and a basic admin/user role.

## Run

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

The API listens on http://localhost:{{BACKEND_PORT}}.

## Endpoints

- `GET /api/health/` — returns `{"status": "ok"}`. No database access,
  no authentication.
- `POST /api/auth/register/` — body `name`, `email`, `password`. Email is
  stored lowercased and must be unique; the password goes through
  Django's validators. Returns 201 with the user (`id`, `name`, `email`,
  `role`); duplicate email and weak passwords are 400. No tokens are
  returned here — log in afterwards.
- `POST /api/auth/login/` — body `email`, `password`. Returns 200 with
  `access` and `refresh` tokens (both also carry `name`, `email` and
  `role` claims). Unknown email or wrong password is 401. The refresh
  token is additionally set as an httpOnly cookie (see below); the
  JSON field stays for backwards compatibility.
- `POST /api/auth/refresh/` — body `refresh`, or nothing: when the body
  has no `refresh` field, the token is read from the httpOnly cookie
  instead. Returns a new `access` token. An invalid, expired or
  blacklisted refresh token is 401.
- `POST /api/auth/logout/` — requires a valid access token plus the
  refresh token, from the body or, when absent, from the httpOnly
  cookie. Blacklists the refresh token, so it can no longer be
  refreshed, and clears the cookie. Missing or invalid refresh token
  is 400.
- `GET /api/auth/me/` — requires auth. Returns the user (`id`, `name`,
  `email`, `role`).
- `GET /api/auth/admin-only/` — example admin-only endpoint: anonymous
  is 401, authenticated non-admin is 403, admin is 200.

## API docs (Swagger / OpenAPI)

- Swagger UI: `http://localhost:{{BACKEND_PORT}}/api/docs/`
- ReDoc: `http://localhost:{{BACKEND_PORT}}/api/redoc/`
- OpenAPI schema (JSON): `http://localhost:{{BACKEND_PORT}}/api/schema/`

The schema is generated by drf-spectacular from the views and
serializers; the login/refresh/logout cookie variants are documented
in the endpoint descriptions, while the schema models the JSON
field path.

## Authentication design

- Tokens: SimpleJWT, access 15 minutes, refresh 7 days (same policy as
  the path-1 backend). Refresh tokens are NOT rotated on refresh; they
  stay valid until they expire or logout blacklists them (the
  `token_blacklist` app is enabled for this).
- httpOnly refresh cookie (SPA adaptation of the path-1 BFF pattern,
  implemented in `api/cookies.py`): login sets `refresh_token` as an
  httpOnly cookie (`SameSite=Lax`, 7-day max age, matching the refresh
  lifetime). The frontend never reads or stores the refresh token —
  the browser sends the cookie automatically, and the backend reads it
  for refresh and logout when the body has no `refresh` field. The
  JSON `refresh` field is kept for backwards compatibility with
  non-browser clients. Two details matter:
  - The cookie path is `/api/auth/`, not just the refresh endpoint:
    logout also needs the token (to blacklist it), and the frontend
    must never hold it to send it in a body. The auth namespace keeps
    the cookie off every non-auth endpoint.
  - Cross-origin cookies need `CORS_ALLOW_CREDENTIALS=1` (default) on
    the API plus `credentials: "include"` on the frontend fetch; the
    origin allowlist (`CORS_ALLOWED_ORIGINS`) still gates which
    origins get credentials. `REFRESH_COOKIE_SECURE` must stay `0` on
    plain `http://localhost` (a `secure` cookie is never sent over
    HTTP) and be `1` in production (HTTPS).
- Roles: every user gets a `Profile` with role `admin` or `user`
  (default `user`), created automatically on registration. The role is
  separate from Django's `is_staff` / `is_superuser`, which only gate
  the Django admin site. Promoting a user is an out-of-band operation,
  for example from the shell:

  ```python
  user = User.objects.get(email="someone@example.com")
  user.profile.role = "admin"
  user.profile.save()
  ```

## Environment

Settings are 100% environment-driven (see `config/settings.py`).
A `.env` file is loaded when present: `backend/.env` first, then the
repository-root `.env` fills any variable not already set. Copy
`.env.example` to `.env` and adjust the values; keep `POSTGRES_*`
identical to the repository-root `.env` used by docker compose.

| Variable | Default | Notes |
| --- | --- | --- |
| `DJANGO_SECRET_KEY` | (generated at startup when unset) | Set a real value in production |
| `DJANGO_DEBUG` | `1` | Set `0` in production |
| `ALLOWED_HOSTS` | `localhost,127.0.0.1` | Comma-separated |
| `POSTGRES_DB` | `{{POSTGRES_DB}}` | Must match compose |
| `POSTGRES_USER` | `{{POSTGRES_USER}}` | Must match compose |
| `POSTGRES_PASSWORD` | (empty) | Must match compose |
| `DB_HOST` | `localhost` | |
| `DB_PORT` | `5432` | |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:{{FRONTEND_PORT}}` | Comma-separated |
| `CORS_ALLOW_CREDENTIALS` | `1` | Lets the browser send the httpOnly refresh cookie cross-origin |
| `REFRESH_COOKIE_SECURE` | `0` | Set `1` in production (HTTPS); must stay `0` on plain http://localhost |
| `DATABASE_ENGINE` | (unset = PostgreSQL) | Set `sqlite` to run the test suite without a PostgreSQL server (local verification only; CI and production use PostgreSQL) |

## PostgreSQL volume gotcha

`POSTGRES_USER` is only created on the first initialization of an empty
volume. Changing the user or password later has no effect until the
volume is removed: `docker compose down -v` (this deletes the data).
